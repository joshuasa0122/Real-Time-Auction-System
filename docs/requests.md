# 다른 담당자에게 보내는 요청

합의 전에는 프로토콜과 코드를 바꾸지 않는다.

## 처리됨 (2026-11-26, PR #4)

변예서 1~6번 모두 반영: `JOIN`의 `SecondsLeft`, `LIST`의 남은 초, `BID`와 `OUTBID`의 `Balance`, 낙찰자 없음 `Winner: -`, 잔액 부족 문구. 끊긴 사용자의 입찰은 유효하게 남는다. README 표에 반영했다.

## 남은 것

## 변예서 (auction): 처리됨, 기록용

1. **`JOIN` 성공 응답에 `SecondsLeft` 헤더 추가**
   - 왜: 경매방 카운트다운에 남은 시간이 필요한데 `JOIN` 응답에 없다. 지금은 `LIST`의 secondsLeft를 쓴다.
2. **`LIST`의 secondsLeft에 실제 남은 초를 넣기** (스텁은 항상 0)
   - 왜: 1번 합의 전까지 카운트다운의 유일한 근거다. 웹은 0을 "알 수 없음"으로 보고 `--:--`를 표시한다.
3. **`BID` 성공 응답과 `OUTBID`에 `Balance` 헤더 추가**
   - 왜: 보증금 hold/release로 잔액이 바뀌지만 화면이 알 방법이 없다. 지금 화면의 잔액은 `LOGIN`, `WON`, `SOLD` 때만 갱신된다.
4. **낙찰자가 없을 때 `CLOSED`의 `Winner` 값 확정**
   - 왜: 웹은 빈 값 또는 `-`를 "낙찰자 없음"으로 처리한다(스텁의 `Leader: -`와 같은 규칙).
5. **잔액 부족 `409`의 `Error` 문구에 `balance`, `money`, `fund`, `enough` 중 하나를 넣기**
   - 왜: 코드가 같은 "금액이 낮음"(`higher` 또는 `low`)과 문구로만 구분할 수 있다.
6. **사용자가 끊겼을 때 정책 결정** (예: 최고 입찰자가 나감)
   - 지금: 서버는 세션에서만 빼고 경매 쪽에는 알리지 않는다. 입찰은 유효하게 남는다.
   - 알려야 한다면 `AuctionService`에 메서드가 필요하므로 팀 합의가 먼저다.

## 변예서 (auction): 새 제안

1. **`Auction`의 `price`, `leader`를 `volatile`로**
   - 왜: 경매 스레드가 바꾸고 `LIST`/`JOIN`은 handler 스레드가 읽는데 메모리 가시성이 보장되지 않는다. 화면은 다음 갱신 때 따라잡아서 지금 증상은 없다.
2. **판매자 본인 입찰을 `400` 대신 `409`로 할지 팀에서 결정**
   - 왜: README에서 `400`은 잘못된 인자, `409`는 요청은 맞지만 지금 상태에서 안 되는 경우다. 웹은 판매자에게 입찰창을 막으므로 화면 영향은 없다.

## 전의령 (gateway, tools)

1. **서버가 먼저 끊을 때 WebSocket close 프레임을 한 번만 보내기**
   - 무엇: `WsGateway.bridge()`에서 receiver 스레드가 close를 보낸 뒤, 브라우저의 close 응답을 받은 메인 루프가 close를 또 보낸다.
   - 왜: 서버를 종료하면 브라우저 콘솔에 `Close received after close` 오류가 찍힌다(2026-11-25 확인). 화면 동작에는 영향이 없다.
